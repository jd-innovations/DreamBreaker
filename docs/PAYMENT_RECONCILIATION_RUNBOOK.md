# Payment Reconciliation Runbook

Operational guide for the **Reconciliation** queue in the admin dashboard
(Admin → Reconciliation). Covers what each queue item means, how to confirm it,
and how to resolve it.

The queue is generated by `admin_payment_reconciliation(p_stuck_minutes, p_limit)`
(migration `20260824190000_payment_reconciliation.sql`). It derives every item
from live table state — never from a flag some writer had to remember to set —
so a code path that fails silently still shows up here.

---

## Ground rules

**1. Stripe is the source of truth for money. This database is not.**
Every item below is a claim that our records and Stripe's disagree, or that our
records and our own domain tables disagree. Before moving money, open the
PaymentIntent in the Stripe dashboard and look at what actually happened.

**2. Never resolve an item by editing `payments.status` directly.**
Payment status transitions come from verified Stripe webhooks only
(`web/src/app/api/stripe/webhooks/route.ts`). Hand-editing a status hides the
problem instead of fixing it, and the next webhook may overwrite it anyway. The
supported repair is to **replay the finalization**, not to fake its result.

**3. An item that disappears on refresh was in flight, not fixed.**
The queue applies a grace period (`p_stuck_minutes`, default 30) precisely so
normal asynchronous lag does not appear here. If something clears on its own it
was slow, not broken — but note it, because repeated slowness is its own signal.

**4. The player comes first.**
Someone in `succeeded_not_fulfilled` has paid and has nothing. Contact them
before you finish diagnosing. "We can see your payment, we're fixing your spot
now" costs nothing and is true.

## `succeeded_not_fulfilled` — critical

**Meaning.** A payment is `succeeded` and the thing it paid for does not exist:
no registration, no confirmed reservation, no finalized purchase, no settled
team obligation. Money in, nothing delivered.

**Where it comes from.** `payment_is_fulfilled()` checks for the exact row that
purpose's finalizer in `web/src/lib/payments/finalizePayment.ts` would have
written. It reports unfulfilled when:

- a finalizer write failed (these also log `PAYMENT_RECONCILIATION_REQUIRED`)
- the deployment has **no finalizer for that `purpose_type`** — an edge function
  created a payment the running web deployment does not know how to complete
- the domain row was deleted or moved on afterwards

**Confirm.**
1. Stripe dashboard → the `provider_ref` PaymentIntent. Is it actually captured?
2. Search the web deployment logs for `PAYMENT_RECONCILIATION_REQUIRED` with
   this payment id. That line names the exact step that failed.
3. If there is no such line, suspect the missing-finalizer case: compare
   `purpose_type` against the branches in `dispatchPaymentSucceeded()`. A
   `purpose_type` with no branch means the web deployment is behind the edge
   function that created the payment.

**Resolve.**
- *Missing finalizer:* deploy the web app so it has that branch, then replay
  (below). This is a deployment-ordering bug, not a data bug — fix the deploy
  first or it will keep happening.
- *Failed write:* fix the underlying cause, then replay.
- *Replay:* re-send the `payment_intent.succeeded` event from the Stripe
  dashboard (Developers → Events → the event → Resend). The handler is
  idempotent per event id, so **delete that event's row from
  `stripe_webhook_events` first** or the redelivery will be deduped away and do
  nothing. Deleting the row is safe: every finalizer is independently idempotent
  (duplicate-registration checks, status guards, `ON CONFLICT` RPCs).
- *Cannot deliver at all* (event passed, slot gone, offer withdrawn): refund it.
  Use the product's own cancel/refund path where one exists so a `refunds` row
  with a policy snapshot is written. A Stripe-dashboard refund leaves no audit
  record here and shows up later as an unexplained `duplicate_payment` or a
  silently refunded payment.

## `stuck_pending` — warning

**Meaning.** A payment has sat at `requires_confirmation` or `processing` since
it was created.

**Usually benign.** Almost always an abandoned checkout: the player opened
PaymentSheet and closed it. Those rows are harmless and never resolve.

**The case that is not benign:** the charge was captured and the
`payment_intent.succeeded` webhook never arrived, so our row never advanced.
From this side of Stripe the two are indistinguishable — which is why these are
surfaced at all.

**Confirm.** Open `provider_ref` in Stripe. `succeeded` there and pending here
means a lost webhook.

**Resolve.**
- *Abandoned:* nothing to do. Consider whether the volume points at a broken
  checkout step.
- *Lost webhook:* resend the event from the Stripe dashboard. There is no
  `stripe_webhook_events` row to delete in this case (the event never landed),
  so it will process normally.
- *Stripe shows `requires_payment_method` / `canceled` and it is old:* nothing
  was captured. Leave it; do not delete rows to tidy the queue.

## `webhook_unprocessed` — critical

**Meaning.** A `stripe_webhook_events` row exists with `processed_at` still
null. The handler recorded the event id, then died or threw before finishing.

**Why this cannot fix itself.** Recording the event id is what makes redelivery
idempotent. Stripe *will* retry, and the retry hits the unique constraint and is
acknowledged as "already processed." Nothing retries these. They are found here
or not at all.

**Confirm.** The item's `detail` names the event type. Cross-check the payment
columns on the same row: if `payment_id` is populated and that payment is
`succeeded` and fulfilled, the work actually completed and only the stamp is
missing — lower urgency.

**Resolve.**
1. Find the root cause in the deployment logs for that timestamp — this is a
   crash, and the next one will do the same thing.
2. Delete the `stripe_webhook_events` row for that `event_id`.
3. Resend the event from the Stripe dashboard.
4. Confirm the item leaves the queue and the payment shows fulfilled.

Do **not** stamp `processed_at` by hand to clear the item. That marks the work
done when it was never performed, and permanently blocks the redelivery that
would have performed it.

## `refund_failed` — critical

**Meaning.** A refund was authorised, recorded, and rejected by Stripe. The
`detail` carries Stripe's own message.

**Why it was not retried automatically.** `cancel-registration` deliberately
does not retry inside the request: a refund that silently retries is how money
goes out twice. The `refunds` row is the retry handle.

**Confirm.** Read `failure_reason`. Common causes:
- *charge already refunded* — someone refunded it in the Stripe dashboard. The
  money is back; the row is wrong. Verify in Stripe, then set the row to
  `succeeded` with `completed_at`.
- *charge not refundable / too old* — Stripe will not reverse it. Needs a manual
  payout or credit; talk to the player.
- *insufficient funds in the platform balance* — top up, then retry.

**Resolve (retry).** The partial unique index on `refunds` excludes `failed`
rows, so a fresh attempt is allowed without touching the old one. Re-run the
product's cancel/refund action for that registration — it will write a new
`refunds` row and call Stripe again. Leave the failed row in place; it is the
record of what happened.

## `refund_stuck` — critical

**Meaning.** A `refunds` row is `pending` past the stuck window, or `submitted`
and unacknowledged for over 24 hours.

- **`pending`:** the obligation was recorded and the Stripe call never happened
  — a crash between the two. This is exactly the gap the write-intent-first
  ordering exists to make visible. **The player has not been paid.**
- **`submitted` for 24h+:** we called Stripe and never saw `charge.refunded`.
  Either the refund is genuinely still pending at the bank (possible — card
  refunds legitimately take days) or the webhook was lost.

**Confirm.** For `submitted`, look up `provider_ref` (the Stripe refund id) in
the Stripe dashboard and read its status. For `pending`, there will be no Stripe
refund at all.

**Resolve.**
- *`pending`:* re-run the product's cancel/refund action. Then cancel the stale
  row (`status = 'canceled'`, `failure_reason` explaining why) so the partial
  unique index does not block the new attempt — do this **first**, or the new
  attempt will be rejected as a duplicate.
- *`submitted`, Stripe says succeeded:* the `charge.refunded` webhook was lost.
  Resend it from Stripe; the handler settles both the payment and the refunds
  row.
- *`submitted`, Stripe says pending:* wait. Note the item and re-check.

## `duplicate_payment` — warning

**Meaning.** The same payer has more than one live (not fully refunded)
`succeeded` payment for the same `purpose_type` + `purpose_id`. The oldest is
treated as the real one; each later one is reported.

**Why idempotency keys did not catch it.** They cover a retried *request*. They
do not cover two devices, or a player who gave up waiting on a slow webhook and
paid again from a fresh session.

**Confirm.** Check whether both payments actually produced something. Some are
legitimate: a player registering for two divisions of the same tournament shares
`purpose_id` (the tournament) but genuinely owes twice. Look at the metadata —
different `divisionId` means it is not a duplicate.

**Resolve.**
- *Genuine duplicate:* refund the later payment. Prefer the product's refund
  path so a `refunds` row with a policy snapshot is written; use
  `kind = 'discretionary'` when it falls outside the cancellation policy, which
  a duplicate does.
- *Not a duplicate* (two divisions, two entries): no action. It will keep
  appearing in the queue — that is the cost of the check being derived rather
  than dismissible, and is preferable to a dismiss button that hides real ones.

## Escalation

| Situation | Action |
| --- | --- |
| Any `succeeded_not_fulfilled` older than 24h | Escalate to engineering. A person is out of pocket. |
| More than ~3 `webhook_unprocessed` in a day | Escalate immediately — the webhook handler is crashing, and each one is money with no domain effect. |
| `succeeded_not_fulfilled` with a `purpose_type` absent from `dispatchPaymentSucceeded()` | Escalate as a deploy-ordering incident. Every payment of that purpose is failing, not just this one. |
| Refund Stripe will not reverse | Escalate to whoever can authorise a manual payout. Tell the player the same day. |
| Queue is empty but a player reports being charged with nothing to show | Do not close it. Check `payments` by `payer_user_id` directly — a payment that never reached `succeeded` is invisible to check 1 by design. |

**What to tell a player, in every case above:** confirm you can see their
payment, say what you are doing, and give a time. Do not promise a refund before
looking at Stripe, and do not promise their spot before confirming it still
exists.

## Tuning the window

The queue is called with a 30-minute grace period by default. While triaging an
active incident, a shorter window surfaces in-flight items:

```sql
SELECT * FROM admin_payment_reconciliation(5, 500);
```

Requires an admin session — the function is `SECURITY DEFINER` and gated on
`is_admin()`, because it reads `stripe_webhook_events`, which is otherwise
locked to the service role.
